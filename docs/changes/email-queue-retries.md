# Transactional email: exclusive send claim, retry backoff, permanent failures, outbox sweeper

**Status:** in progress. Step 1 shipped in #169, step 2 in #170 and #171; step 3 (this branch) awaiting review. Steps 4–6 of #162 are planned.
**Touches:** `packages/server/src/services/{email-delivery.service,email-error,email.service}.ts`, `packages/server/src/queues/{worker,emailBackoff,dlq-consumer}.ts`, `packages/server/src/jobs/emailOutboxSweeper.ts`, `packages/server/src/index.ts`, `packages/server/src/config/{env,emailSender,constants}.ts`, `packages/server/src/ops/probes/backlog.ts`, `packages/server/src/db/schema/emailDeliveries.ts`, `packages/server/drizzle/{0014_email_delivery_claim_lease,0015_email_delivery_send_epoch}.sql`, `docs/runbooks/email-mass-failure.md`
**Ships with:** #169 (step 1), #170 and #171 (step 2), `feat/email-outbox-sweeper` (step 3). Tracking issue #162.

## 1. What the code does today

Every transactional email is a row in `email_deliveries`, created by `dispatchEmail`. In production `SQS_QUEUE_URL` is not set, so the row is sent inline and a failure is attempted once. The queue path already exists: `dispatchEmail` enqueues `{ deliveryId }`, and `startEmailSqsWorker` in `server` calls `attemptEmailDelivery`. #162 turns that path on. Before it is on, three things had to be true that were not.

**The claim was not exclusive (fixed in step 1).** The claim was:

```ts
.set({ attempts: sql`${emailDeliveries.attempts} + 1`, lastAttemptAt: new Date() })
.where(and(eq(emailDeliveries.id, deliveryId), eq(emailDeliveries.status, "PENDING")))
```

It collapsed a read-then-write into one statement, which is the right instinct. But the status stays `PENDING` for the whole provider call, so a second consumer arriving mid-send matched the same row. With inline sending nothing else ever arrived. With a queue, an SQS redelivery or the planned outbox sweeper does.

**Retries had a fixed delay (step 2).** On failure the message was left undeleted and came back after the receive's 60s visibility timeout, every time.

**Every failure was retried, and every failure was recorded as "Unknown error" (step 2).** The catch was:

```ts
const message = err instanceof Error ? err.message : "Unknown error";
```

The senders in `email.service.ts` rethrow Resend's `error`, and the Resend SDK returns that as a plain object, `{ name, statusCode, message }`, not an `Error`. A real call with an invalid key returned `{"statusCode":401,"name":"validation_error","message":"API key is invalid"}` with `instanceof Error` false. So `failure_reason` never held the provider's message. And an email with an invalid recipient would be retried until the redrive policy gave up on it.

## 2. What I am changing, and why

**Step 1 (#169): a lease, and `failed_at`.**
- `claimed_until`: the claim matches only when no unexpired lease exists. Today a second consumer sends the same email twice; reproduced against Postgres both sequentially and with overlapping transactions.
- A lease, not a `SENDING` status: `notification_delivery_status` is shared with `notification_deliveries` and mirrored in `@application/shared`.
- `attemptEmailDelivery` returns `sent | skipped | deferred`. On `deferred` the worker keeps the message and hides it for the lease length. Deleting it would drop the email if the lease holder died, and leaving it at 60s would spend a receive each time it came back.
- `failed_at`: Ops Console counted failures by `created_at`. A delivery fails only after its retries run out, often more than an hour after it was created, so it was never counted.

**Step 2 (this branch): backoff, permanent failures, readable reasons.**
- **Backoff** (`queues/emailBackoff.ts`). A failed message is hidden with `ChangeMessageVisibility` for 30s, 2m, 5m, then 15m for every later receive, plus up to 20% jitter, keyed on `ApproximateReceiveCount`. The receive now asks for that attribute; without it the attribute is absent and every failure would wait the first delay. With the planned `maxReceiveCount` of 8 a message is retried for a little over an hour. With the old fixed 60s delay and that same redrive policy, a Resend outage would exhaust the receives in about 8 minutes, so a short outage would turn into permanent failures.
- **Permanent failures** (`services/email-error.ts`). A 400 or 422 `validation_error`, `missing_required_field`, `invalid_parameter` or `invalid_attachment` marks the row `FAILED` through `markEmailDeliveryFailed` (so `failed_at` is set) and returns `failed`, and the worker deletes the message. Retrying gets the same answer: today a bad address is sent 8 times and only reaches `FAILED` an hour later.
- **Everything else retries**, including anything unrecognised. The configuration errors retry on purpose: an invalid, missing or restricted API key (Resend reports an invalid key as `validation_error` 401) and an unverified domain (403). They are shared by every email and fixed by a redeploy, so failing each email fast would lose all of them. Rate limits, quota errors and `application_error` retry too; `application_error` with a null status is what the SDK returns when the request never reached Resend.
- **`RESEND_FROM_EMAIL` is validated at startup** (`config/emailSender.ts`): an address or `Name <address>`, trimmed. A malformed sender is configuration too, but Resend's current error reference has no `invalid_from_address` row (only the SDK type does), so it most likely comes back as a 400/422 `validation_error`, which is classified permanent: every email would be marked `FAILED`. It was `z.string()`, and `docker-compose.prod.yml` passes `${RESEND_FROM_EMAIL}` with no default, so a missing SSM parameter arrived as `""` and passed (`.default()` only replaces `undefined`). Now the process exits at boot and the deploy fails loudly instead. Not verified against the live API, which needs a real key; the check makes the answer irrelevant.
- **Idempotency key per delivery.** Every send passes `idempotencyKey: email-delivery/<deliveryId>` to Resend, which treats a repeat with the same key within 24 hours as the first request and does not deliver it again. The lease alone left two ways to send twice: the email goes out but the `SENT` write fails (a database blip), so the retry sends again (reproduced with a unit test: two provider calls); or the Resend SDK, which sets no request timeout, hangs past the 120s lease and a second consumer claims the row. Retries end after about an hour, well inside the 24-hour window. A repeat with a different body is rejected (409 `invalid_idempotent_request`); the email renders from the stored row, and the only time-dependent part is the footer year, so that happens only for a retry spanning New Year.
- **Recovery from a mass failure: `requeueFailedEmailDeliveries({ type, failedSince, limit })`.** Failing fast has a cost: a deploy that breaks one email type's request makes every email of that type `FAILED` on its first attempt, and with the queue on those rows would otherwise have recovered on their own if the fix landed within the retry window. Today nothing brings them back. The function puts matching `FAILED` rows back to `PENDING` and delivers them (enqueued if SQS is configured, inline otherwise). It skips rows whose link has expired (from `created_at`: verification and invite 24h, reset 1h) and rows attempted within the claim lease (the DLQ drain can mark a row `FAILED` mid-send). Each re-send increments `send_epoch` (migration 0015), which is part of the idempotency key: Resend does not document whether it caches a rejected request against its key, and if it does, a re-send under the old key would deliver nothing. The batch is chosen by a `MATERIALIZED` CTE: the first version used `UPDATE … WHERE id IN (SELECT … LIMIT … FOR UPDATE SKIP LOCKED)`, which Postgres re-scanned once per outer row, and the limit test re-sent 3 rows with `limit: 2`. Runbook: `docs/runbooks/email-mass-failure.md`.
- **`describeEmailError`** records `name status: message` for provider errors. Today every failure in `failure_reason` reads "Unknown error".

**Step 3 (this branch): the outbox sweeper.** A row can be `PENDING` with nothing left to send it: the enqueue failed after the row was saved (`dispatchEmail` throws, and every caller logs and carries on), an inline send failed with no queue to retry it, or its message redrived to the DLQ and was never drained. `sweepPendingEmailDeliveries` runs every 5 minutes (`jobs/emailOutboxSweeper.ts`, in `server`) and handles those rows:
- **Never attempted, older than 10 minutes:** sent on. With the 5-minute poll, within 15 minutes of creation.
- **Attempted, and no attempt for 1 hour 46 minutes:** sent on. That wait is the whole SQS retry ladder with full jitter (`emailRetryLadderSeconds`, 99 minutes, from `EMAIL_MAX_RECEIVE_COUNT` = 8, which must match the redrive policy), plus one DLQ drain and the claim lease. Any sooner, a message may still be retrying the row, and a second message would start a ladder of its own.
- **Too old to send:** closed `FAILED` (`Expired before it could be sent`, appended to the provider's last error). The limit counts from `created_at`: `reset-password` 1 hour, every other type 24 hours. The 24 hours is Resend's idempotency window: past it, re-sending a row whose earlier send did go out (its `SENT` write failed) would deliver it twice. Types with no link expiry need the explicit `ELSE`; without it the lifetime is `NULL` and those rows are silently never swept.
- **24 attempts (3 × the receive count):** closed `FAILED` (`Gave up after N attempts`). A loop breaker, not a retry budget: a requeue keeps `attempts`, so a cap at 8 would close rows SQS is still legitimately retrying.
- **A live claim:** left alone.

A swept row is sent under the idempotency key it already had, with no `send_epoch` bump, unlike a requeue: if the earlier attempt went out, the same key is what lets Resend drop the repeat. The send selection re-checks age as well, so an expired row the close-out had no room for (batches of 100) is never sent; a test caught that.

**Lock:** Redis, like `attendanceWindowNotifier`, not a Postgres advisory lock. It only saves duplicate work: the close-out uses `FOR UPDATE SKIP LOCKED` and every send goes through the claim, so two concurrent sweeps are safe. When Redis is down the sweep runs without the lock, so email recovery does not depend on Redis. Only `server` runs jobs today (`ops-server` and `pdf-worker` have their own entry points), so there is one runner.

`DLQ_DRAIN_INTERVAL_MS` moved from `queues/dlq-consumer.ts` to `config/constants.ts`: the service needs it, and `dlq-consumer` imports the service.

## 3. What this affects

- **Production today (inline sending):** a permanent rejection now ends as `FAILED` instead of `PENDING` forever, and `failure_reason` is readable. A retryable inline failure logs `email.inline_failed_not_retried`; with step 3 the sweeper sends it again 1 hour 46 minutes later, until 24 attempts or its expiry.
- **Step 3 on first deploy:** the sweep runs at boot over every `PENDING` row. Migration 0014 closed rows older than a day; a row between its link lifetime and a day old is closed `FAILED` and counts once in `emailFailed1h`. Production had 7 deliveries, all `SENT`, when checked on 2026-09-15. Signals: `email.outbox_swept` (counts per run), `email.delivery_abandoned` (one per closed row, with `reason`), `email.outbox_sweep_failed`.
- **Step 3 while sending is inline:** until the queue is on (step 5), swept rows are sent inline inside the job, one at a time, up to 100 per run. A slow Resend makes a run long; the lock expires after 4 minutes, and an overlapping run is safe.
- **Ops Console:** a permanent rejection counts in `emailFailed1h` straight away. A bad recipient in a broadcast can turn the backlog badge amber or red where it used to stay green. That is the intent: it was always failing.
- **Queue path (off until step 5):** with no redrive policy yet, a retryable message keeps retrying at 15-minute intervals until the queue's message retention period expires. The redrive policy and email DLQ in #162 step 6 bound that.
- **User impact of a mass failure** (what the runbook's recovery is for): `verification` blocks login (`auth-login.service.ts` requires a verified email) and resend-verification fails the same way until fixed; `reset-password` blocks resets; `invite` leaves invitees without a link; `report-ready`, `event-*` and `org-broadcast` lose only the email copy (in-app and push still go out). In production today (inline sending) failing fast loses no email that would otherwise have been delivered, since inline sending never retried.
- **Startup:** a deploy with an empty or malformed `RESEND_FROM_EMAIL` now fails at boot. The current production value already sends verification and reset emails, so it is valid and unaffected.
- **Classification mistakes:** a transient error classified as permanent would lose an email. The permanent set is limited to request-shape errors with a 400/422 status, and anything unrecognised retries. Signal: `email.delivery_failed_permanently` log lines and `FAILED` rows whose `failure_reason` is not about the recipient or content.
- **Idempotency:** Resend's dedupe itself is not tested here (needs a real key); the tests prove every sender forwards the key and every retry of one delivery repeats it. A repeat that Resend dedupes returns success, so the row is marked `SENT` without a second email. A 409 `invalid_idempotent_request` retries (not in the permanent set) and would reach the DLQ.
- **Signals if it breaks:** `email_sqs.process_failed` logs now carry `receiveCount` and `retryInSeconds`. A `retryInSeconds` that never grows means the receive count is not arriving.

## 4. What to learn from this

- **An atomic claim must change what the next claimant checks.** A conditional `UPDATE … WHERE status = 'PENDING'` is only a mutex if it moves the row out of `PENDING`, or sets a lease the condition also checks. Spot it: find the claim's `WHERE` and ask whether the `SET` makes that `WHERE` false for the next caller.
- **Classify failures as retryable or permanent, and default unknown to retryable.** Retrying a permanent error wastes the retry budget and delays the signal. Failing a transient one loses work, which is worse. Classify on what the error means, not its HTTP class: here one error name covered both a bad recipient (422) and a bad API key (401).
- **`LIMIT` in a locking subquery of an `UPDATE` is not a bound.** Postgres may rescan `IN (SELECT … LIMIT n FOR UPDATE SKIP LOCKED)` per outer row; a rescan re-checks rows the statement already changed, skips them, and takes the next. Select the batch once in a `MATERIALIZED` CTE. Spot it: `EXPLAIN ANALYZE` shows `loops` > 1 on the `LockRows` node.
- **Validate configuration where it is loaded, not where it is used.** A bad setting that is only discovered per request looks like a per-request failure, and error handling built for those (here, fail fast on a 4xx) does the wrong thing at scale. Spot it: an env var typed as a bare string that a third party will parse; and `${VAR}` in compose with no default, which turns a missing value into `""`.
- **Check what a library actually throws.** `err instanceof Error ? err.message : "Unknown error"` silently discards the diagnostic when a library returns plain error objects, as the Resend SDK does. Spot it: any `instanceof Error` fallback around a third-party call; call the library once with bad input and look at the object.
- **A lock narrows a race; an idempotency key closes it.** A lease stops two workers sending at once, but not a retry after work that succeeded and failed to record it (*at-least-once delivery*). The fix is making the side effect itself idempotent at the provider. Spot it: any external call followed by a separate write that records it; ask what happens when the call succeeds and the write fails.
- **Derive an outbox's quiet period from the retry policy.** Re-driving a row whose message is still being retried creates a second message with a fresh receive count. Spot it: a "re-enqueue stale rows" job whose staleness threshold is a literal rather than computed from the queue's backoff and max receive count.
- **Recovery must not outlive the dedupe window.** An idempotency key protects a retry only while the provider remembers it. Spot it: a retry or sweep with no age limit around a call that relies on an idempotency key.
- **Exponential backoff with jitter** spreads retries out so a recovering dependency is not hit again by every failed message at the same moment (the *thundering herd*).
